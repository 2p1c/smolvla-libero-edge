# 简历条目与面试要点

## 简历条目

按投递方向选一个版本。每一条都是“动作 + 方法 + 带单位的数字 + 对比基准”，所有数字都能在 README 里找到出处。

### 版本 A：VLA 微调 / 部署岗

**SmolVLA 视觉-语言-动作模型微调与部署分析**（LeRobot · LIBERO · MuJoCo · PyTorch）

- 基于 LeRobot 在 LIBERO（1693 条演示）上微调 4.5 亿参数的 SmolVLA，搭建“数据审计 → 训练 → 闭环仿真评测 → 配对统计对比”的自动化流水线；LIBERO-Spatial 成功率 78%，高于官方 checkpoint 的 69%（各 100 回合，逐回合配对比较）。
- 闭环消融动作块执行步数：发现微调模型继承的默认值 n=50 会让开环执行长达 2.5 秒，改为 n=10 后成功率 68% → 78%，零额外训练；同时证明 n=10 相比 n=1 没有损失（配对 p=1.0），可以把推理频率要求从 20 Hz 降到 2 Hz。
- 用 torch.profiler 定位到推理受限于 CPU 下发 kernel 的开销（约 2.4 万个 kernel，GPU 实际计算只占 57 ms），因此改用 torch.compile 算子融合并把去噪步数减半，单次推理 266 → 37 ms（7.2×），闭环成功率保持在 81%；得出 RTX 4090 上 20 Hz 控制的可部署配置。
- 排查训练与部署的一致性：验证相机方向与映射、归一化统计量（差异 0.0000σ），发现评测渲染分辨率（360 px）与训练数据（256 px）不一致，对齐后官方模型 69% → 75%。

### 版本 B：机器人数据工程岗

**机器人演示数据审计与数据配比实验**（LeRobot v3 数据集 · pandas · LIBERO）

- 编写数据审计工具，1 分钟内完成 1693 条演示、27 万帧的体检：suite 配比、长度分布、静止帧、夹爪行为、动作饱和度、异常回合，以及归一化统计量和模型 checkpoint 的一致性校验。
- 发现评测目标 suite 只占训练帧的 19%，数据集的 fps 元数据有误（标 10 Hz，实际 20 Hz），两个 suite 的最长演示已用到评测步数上限的 90%–97%；用同一任务内的相对规则替代全局阈值，消除了 76 条异常误报。
- 设计单变量数据配比实验：只用 26% 的数据（spatial 子集）、一半的训练步数，目标任务成功率 80%，与全量数据模型的 78% 持平（逐回合配对 McNemar p=0.83）。
- 建立评测规范：固定种子、配对比较、Wilson 置信区间，并人工标注失败回合（74% 是抓错了目标物体），把“成功率差几个点”变成可检验的结论。

## 面试时一定会被追问的点

**“78% 和 69%，是显著提升吗？”**
不显著。100 回合时，95% 置信区间约为 ±8 个百分点；逐回合配对 McNemar 检验 p = 0.14。我报告的是方向和 p 值。要下显著性结论，大约需要 300 回合以上，或者让差异更大。

**“为什么你测的官方模型比论文的 90% 低？”**
评测设置不同。我排除了相机方向问题，发现分辨率不一致，对齐后有改善但不显著。第三方复现也报告过更低的数字。我的所有对比都在同一设置下进行，所以相对结论成立；绝对数字不和论文直接比。

**“BF16 为什么没变快？”**
因为瓶颈不在 GPU 计算。profiler 显示 GPU 只算了 57 ms，其余时间耗在 CPU 逐个发起 2.4 万个小 kernel 上。降精度减少的是计算量，不减少 kernel 数；compile 做算子融合，直接减少 kernel 数，所以有效。

**“n_action_steps 怎么选？”**
看两条曲线的交点：一条是“成功率 vs n”（闭环消融得到），另一条是“硬件允许的最小 n”（⌈p90 延迟 / 控制周期⌉）。在 4090 上，后者在优化后是 1，所以选成功率不掉的最大 n（10），给推理留出余量，也方便以后换到更弱的端侧设备。

**“只用 spatial 数据为什么没有明显更好？”**
两种可能：一是全量数据里其他 suite 的抓取、放置技能对 spatial 也有帮助（正迁移）；二是 100 回合分辨不出 2 个百分点的差异。结论应该写成“用 26% 的数据、一半的计算达到相当水平”，这是数据效率上的收益，不是精度上的收益。

**“如果要部署到 Jetson Orin？”**
先在 Orin 上测同样的延迟表，看“20 Hz 下最小 n”。如果 n ≤ 10，就沿用本项目的成功率曲线；如果更大，就需要 TensorRT 导出、INT8 量化、减少视觉 token 等手段，再回到闭环里重新验证成功率。

## 这一天形成的可复用技能

- 先冒烟测试、实测吞吐量，再做计算预算；长任务后台化（`setsid nohup` + 日志 + 退出码），tmux 只用来看日志。
- 无头环境里“没报错但卡住”，十有八九是在等输入（交互提问、静默下载）：长任务一律加 `< /dev/null`。
- 拿到数据集先体检，异常规则要用领域知识校验。
- 部署参数（n_action_steps、去噪步数、分辨率、并行数）都是超参数，要在闭环里扫，并且要比较的实验保持其他设置完全相同。
- 能配对就配对，所有成功率都带回合数和置信区间。
- 延迟要在 GPU 独占时测；先用 profiler 找瓶颈，再选优化手段。
